# 上傳照片先正規化再辨識、存檔

上傳的照片（保健食品標示、藥包）在辨識與存檔之前，統一正規化成同一種 JPEG：依 EXIF 方向轉正、長邊大於 1600 px 時等比例縮小（不放大）、轉 RGB（透明部分補白）、以品質 85 重新編碼，不帶任何中繼資料。VLM 看到的，就是物件儲存存下來的那一張；兩條照片路徑（保健食品、藥包）共用同一個函式 `photo_normalization.normalize_photo`，VLM eval 送出照片前也套用它，量到的就是使用者實際得到的。

原有的魔術位元組檢查與 10 MB 上限保留，作為解碼前的第一道關卡；通過後才用 Pillow 解碼。解碼失敗，或像素數超過 Pillow 的 `MAX_IMAGE_PIXELS`（解壓縮炸彈防護，超過就直接拒絕，不等 Pillow 的兩倍門檻），回 422 請使用者重拍或換一張，此時不存任何物件、也不呼叫 VLM。

## 為什麼

- **回頭查讀錯時才準**：存的就是模型看到的。若存原圖、送縮圖，查「為什麼讀成這樣」時看到的不是模型看到的。
- **中繼資料不保留**：手機照片常帶 GPS 與裝置資訊，系統用不到，存了只是隱私負債。重新編碼就不會帶 EXIF、ICC、XMP、註解。
- **延遲與費用下降**：手機原圖動輒數 MB、上千萬像素，縮到長邊 1600 px 後標示上的小字仍讀得清楚，檔案與 VLM 的影像 token 都小很多。
- **EXIF 方向在儲存前處理掉**：去掉 EXIF 後方向資訊就沒了，所以要先轉正再存，否則橫躺的照片會永遠橫躺。

## Consequences

- 拿不回原始解析度：之後若想用更高解析度重讀，只有 1600 px 的版本可用。
- 一律輸出 JPEG：PNG／WebP 的無損與透明度不保留（透明補白）；存檔的 MIME 一律 `image/jpeg`、副檔名 `.jpg`。
- 已經存在的舊物件不轉換，維持原格式；程式不假設物件一定是 JPEG。
- 上傳端點多一次解碼與編碼的 CPU 成本；照片數上限（每項 8 張）與 10 MB 上限使其可接受。
- 測試改用 Pillow 產生的真實小圖（`tests/images.py`），魔術位元組湊出來的假圖過不了解碼。
